DDD in 2 Minutes — The Core Idea

If you've never seen DDD before, read this first. Three ideas. Everything else follows from these.

The Core Ideas

Three ideas that make DDD click

🤔

The Problem

Without structure, code becomes a mess. Business rules scatter across dozens of files. Change one thing → break ten others.

💡

The Solution

DDD says: objects should enforce their OWN rules. The User class decides if you can ban someone — not a separate policy file.

🎯

The Result

Every rule lives in exactly one place. Easy to test, easy to change, impossible to accidentally skip validation.

🗣️ In Plain English
Think of a vending machine. You can't open it and grab a snack. You press a button, the machine checks if you paid, checks stock, then gives you the snack or refuses. The machine applies its own rules — always. No shortcut possible.

DDD does the same for your code. You call user.ban(requesterId, days) and the User object checks all the rules itself. You can't accidentally skip the check.
🎰 Vending Machine vs DDD Object — Same idea, different world
"An object enforces its own invariants."

Every rule, every guard, every validation lives inside the object that owns it. Nothing outside can bypass it. Memorise this one sentence — it IS DDD.

Part 1 — Architecture

The 4 Layers — A Building with Strict Floors

Every file in your project belongs to exactly one layer. Each layer only talks to the layer directly below it. Never above, never skipping.

Architecture

The 4 Layers — visual breakdown

🍽️ Restaurant Analogy — Read This First
A restaurant has strict roles: Waiter takes orders from customers (Presentation) → hands to Manager who organizes the kitchen (Application) → Chef knows recipes and rules (Domain) → Kitchen equipment and ingredients are used (Infrastructure).

The Chef never talks directly to customers. The Waiter never cooks. Each person has exactly one job. This is why the restaurant runs smoothly. DDD layers work the same way.

The Iron Law — Never Break This
Domain NEVER imports from Infrastructure. Infrastructure NEVER imports from Presentation. Each layer talks only to the layer directly below it. Break this once → spaghetti code in weeks.
Coding Order

Which file do you write first?

Always start from Domain (no dependencies), then work outward. Never write a file that depends on something you haven't written yet.

Part 2 — Domain Layer

Steps 1–6: Value Objects, Events, and the Aggregate

The heart of DDD. This is where all business rules live. Start here, always.

Steps 1–3

Value Objects — Smart Wrappers

🗣️ In Plain English
A Value Object is a wrapper around a primitive (string, number, date) that adds validation. Instead of passing a plain string for email everywhere, you pass an Email object that guarantees it's always valid. You can never have an invalid email anywhere in your system because it would have thrown an error when created.
❌ Without Value Object
// email is just a string
// nothing stops this:
const email = "not-an-email";
// valid string, invalid email
// you only find out when you
// try to send a real email 💀
✅ With Value Object
// throws immediately if invalid
const email = new Email("not-an-email");
// ↑ Error: Invalid email!

// You can NEVER have a bad email
// in your system. ✅
1
UserId Value Object — Simplest possible file
domain/value-objects/user-id.vo.ts
Wraps a string but refuses to exist if it's empty. Every other file imports this, so write it first.
user-id.vo.ts
export class UserId {
  private readonly _value: string;

  constructor(value: string) {
    if (!value) throw new Error('UserId cannot be empty');
    this._value = value;
  }

  get value(): string { return this._value; }
  equals(other: UserId): boolean { return this._value === other._value; }
}
Step 6 — The Big One

The Aggregate — a fortress around your business rules

🗣️ In Plain English
The Aggregate is the main object in your domain. Think of it as a fortress. Inside the fortress, all the business rules live. Nobody gets in or out without going through the gate (a public method). You call user.ban() — the gate — and the fortress checks everything internally. You can never bypass the fortress to modify user data directly.
🏰 The Aggregate "Fortress" — User Aggregate
🧠 User Aggregate — ban() method walkthrough
What ban() does internally
1. this._canBan(requesterId)
Private guard: checks requesterId exists, isn't banning self, isn't banned themselves
2. this._props.status = 'banned'
Actually mutates the state — only happens AFTER guards pass
3. this._props.banPeriod = BanPeriod.forDays(days)
Calculates ban end date using the BanPeriod value object
4. this.raise(new UserBannedEvent(...))
Records the event — to be published after this is saved to DB
🎯 Real World Example — what happens when UserAppService calls ban()
// application/user.app.service.ts
async banUser(requesterId: string, targetId: string, days: number) {
  // 1. Load from DB → get full User aggregate
  const user = await this.repo.findById(new UserId(targetId));

  // 2. Call the command — User checks ALL its own rules
  user.ban(requesterId, days);  // throws if not allowed ✅

  // 3. Save the updated user to DB
  await this.repo.save(user);

  // 4. Collect events from the aggregate and publish
  const events = user.pullEvents();
  await this.eventBus.publish(events);
}

The Application Service is a workflow coordinator only. It does NOT make decisions — that's the aggregate's job. It just loads, calls, saves, dispatches.

Step 4 — Domain Events

Domain Events — the aggregate's notification system

🗣️ In Plain English
When something important happens inside the aggregate (user banned, user deleted), it "raises" an event — like posting a note on a bulletin board. The event is just a record: "this thing happened, here is the data." The aggregate doesn't care who reads the bulletin board. It just posts and moves on. Later, other parts of the system read the bulletin board and react.
⚡
The 4-Step Event Flow (Inside One Module)
1. Aggregate method runs → calls this.raise(new UserBannedEvent(...))
2. App service calls user.pullEvents() to collect the events
3. App service saves the user to DB, then calls eventBus.publish(events)
4. Event bus routes to registered handlers (e.g. send email, clean up data)
domain/events/user-banned.event.ts
export class UserBannedEvent {
  readonly type = 'user.banned';  // ← used by EventBus to route

  constructor(
    public readonly userId:     string,
    public readonly requesterId: string,
    public readonly banEndDate:  Date,
  ) {}
}
// Rule: events only contain primitive data (strings, dates)
// Never reference domain objects inside an event

The Port Pattern (Interface = Contract)
Domain defines IUserRepository (an interface). Infrastructure implements it. Domain only knows the contract, not the implementation. This means you can swap MongoDB for PostgreSQL by writing a new class that implements IUserRepository — zero other files change.

export interface IUserRepository {

  save(user: User): Promise<void>;
  hardDelete(id: UserId): Promise<void>;
  findAll(): Promise<User[]>;
}

Part 4 — The Most Important Section

Decoupling — How Modules Talk to Each Other

This is where most beginners get stuck. Read this slowly. Every diagram here is designed to make it click visually.

The Problem

Why modules shouldn't talk directly

🗣️ In Plain English — The Spaghetti Problem
Imagine 4 people in a group project: User, Vendor, Order, Notification. If every person calls every other person's phone directly, you get chaos. When one person changes their phone number, everyone needs to update their contacts. This is what happens when modules import each other directly.

The solution: instead of calling each other's phones, everyone posts messages to a central message board. Nobody needs to know anyone else's phone number anymore.
❌ Direct Imports — The Problem
✅ Via Bus/Events — The Solution
🔑
The Key Insight
Modules should only depend on contracts (tiny query classes or interfaces), never on each other's implementations. When the implementation changes, only the handler inside the owning module needs to adapt — everyone else is insulated.

3 Patterns to Achieve Decoupling

🚌

QueryBus

Send a query object to a bus. Bus routes it to a handler inside the owning module. Caller only imports a tiny data class.

Best for: "I need data from another module RIGHT NOW"
🛡

Anti-Corruption Layer

A thin wrapper file in the consumer module. Calls the other module's service but translates types locally.

Best for: Same team, stable dependency, quick win
⚡

Domain Events

Publish an event. Subscribers react independently. The publisher doesn't know who's listening.

Best for: "React to something that happened elsewhere"
Pattern 1 of 3

🚌 QueryBus — Synchronous data reads

🗣️ In Plain English — The Restaurant Order Analogy
At a restaurant, you (VendorService) don't walk into the kitchen to ask the chef (UserInternalService) directly. You write your order on a ticket (GetUserByIdQuery) and give it to the waiter (QueryBus). The waiter goes into the kitchen, gets the answer, and brings it back to you. You never touched the kitchen.

If the kitchen restructures, you don't care. Your ticket (the query class) stays the same. The kitchen (User module) updates their internal handler. You (Vendor) are completely insulated.

Pattern 2 of 3

🛡 Anti-Corruption Layer — Type isolation

🗣️ In Plain English — The Currency Exchange Analogy
Imagine you're in France and you want to buy something at a UK shop. You have Euros; they accept Pounds. You go to a currency exchange office (the ACL). You give Euros, get Pounds. The shop never sees your Euros. You never deal with Pounds directly.

ACL works the same way: VendorService has its own types (VendorUserView). UserInternalService returns UserReadModel. The ACL sits between them and translates — so types from one module never pollute the other.
🛡 ACL — Type Translation Between Modules
vendor/infrastructure/user-acl.ts — lives IN Vendor, not in User!
import { UserInternalService } from '@user/application/user.internal.service';
import { VendorUserView } from '../domain/vendor-user-view';

export class UserACL {
  constructor(private userSvc: UserInternalService) {}

  async getOwnerView(userId: string): Promise<VendorUserView | null> {
    const user = await this.userSvc.getById(userId);
    if (!user) return null;
    // Only expose what Vendor actually needs
    return { ownerId: user.id, ownerName: user.username };
  }
}
// VendorService imports UserACL, NEVER UserInternalService directly
⚠️
ACL vs QueryBus — Key Difference
ACL still imports the other module's class directly. If UserInternalService is renamed, ACL breaks. QueryBus doesn't. Use ACL for stable, same-team deps where you just want type isolation. Use QueryBus for volatile or cross-team deps where you want maximum insulation.
Pattern 3 of 3

⚡ Domain Events — Zero-coupling reactions

🗣️ In Plain English — The News Notification Analogy
When a news website publishes a story, it doesn't call CNN, BBC, and every news app individually. It posts the news (publishes an event). All the apps that subscribed to that news topic get notified and react on their own.

Domain Events work exactly like this: when a user is deleted, UserAppService publishes UserDeletedEvent. It does not know or care who's listening. VendorModule subscribed, so it reacts and deletes the vendor's listings. NotificationModule subscribed, so it sends a goodbye email. User module imports zero other modules.

Pattern 4 of 4 — Synchronous Decoupled Writes

🚦 The Command Bus — Synchronous Decoupled Commands

The missing piece between QueryBus (reads) and EventBus (async reactions). For synchronous writes that must succeed atomically — before the caller can proceed.

You already have two buses. But there is a gap that trips up every team eventually — and it's where overselling bugs and race conditions quietly hide.

🚌 QueryBus
Synchronous Reads
"Give me data right now." Caller awaits result. Fully decoupled. ✅ Already built.
🆕 This Section
🚦 CommandBus
Synchronous Writes
"Do this right now and confirm." Caller awaits confirmation. Atomic. Decoupled.
⚡ EventBus
Async Reactions
"Something happened — react when ready." Fire-and-forget. ✅ Already built.
🗣️ In Plain English — The CEO Order Analogy
A CEO gives a direct order to a department head: "Reserve 3 units of SKU-42 right now — and confirm when it's done." The CEO signs the purchase order only after confirmation arrives. The CEO doesn't attend inventory meetings, touch the warehouse system, or know how reservations work internally. They just issue the command and await the result.

The Command Bus is that same intermediary. OrderAppService (the CEO) sends a ReserveInventoryCommand to the bus. The bus routes it to ReserveInventoryHandler (the department head) deep inside the Inventory module. The result comes back synchronously. OrderService never knew how inventory works internally — and that is the whole point.
💥
Why Not Use Domain Events for Inventory Reservation?
If you fire a StockReservationRequestedEvent and immediately save the order, you have a race condition:
1. Order saves to DB ✓  2. EventBus handler tries to reserve — but stock is already at zero from a concurrent order  3. Reservation fails — but the order is already committed. You oversold. 💀

The CommandBus keeps it atomic: await reserve() → if that throws → order is never saved. If it succeeds → order saves. Strict sequence. Zero race window.

🔩 Core Interfaces — Mirror of QueryBus

shared/domain/i-command.ts — The 3 interfaces you need
// 1. Marker interface — every command class implements this
export interface ICommand<TResult = void> {
  /* intentionally empty — used for type-safety at the bus level */
}

// 2. Every command handler implements this (mirror of IQueryHandler)
// TResult is declared FIRST so TCommand's constraint can reference it directly
export interface ICommandHandler<
  TResult = void,
  TCommand extends ICommand<TResult> = ICommand<TResult>,
> {
  handle(command: TCommand): Promise<TResult>;
}

// 3. The bus contract — wire this in your DI container (mirror of IQueryBus)
export interface ICommandBus {
  register(
    commandName: string,
    handler: ICommandHandler<any, any>,
  ): void;
  execute<TResult>(command: ICommand<TResult>): Promise<TResult>;
}
shared/infrastructure/in-memory-command-bus.ts — Same pattern as InMemoryQueryBus
export class InMemoryCommandBus implements ICommandBus {
  private handlers = new Map<string, ICommandHandler<any, any>>();

  register(
    commandName: string,
    handler: ICommandHandler<any, any>,
  ): void {
    this.handlers.set(commandName, handler);
  }

  async execute<TResult>(command: ICommand<TResult>): Promise<TResult> {
    const name = command.constructor.name;
    const handler = this.handlers.get(name);
    if (!handler) {
      throw new Error(`No handler registered for command: ${name}`);
    }
    return handler.handle(command) as Promise<TResult>;
  }
}
// Identical pattern to InMemoryQueryBus — just "command" instead of "query" ✅

📦 The Command and its Handler — the 4-file pattern

A
The Command — a tiny data bag (public, in Inventory module)
inventory/application/commands/reserve-inventory.command.ts
Just a data bag — no logic. This is the only thing OrderModule ever imports from InventoryModule. Keep it tiny and stable; if it changes, all callers need updating.
export class ReserveInventoryCommand implements ICommand<void> {
  constructor(
    public readonly items:   Array<{ skuId: string; quantity: number }>,
    public readonly actorId: string,
  ) {}
}
// OrderModule imports ONLY this 5-line class from Inventory
// It never sees InventoryInternalService, InventoryRepository, or InventoryAggregate
B
The Handler — private, lives inside Inventory module only
inventory/application/command-handlers/reserve-inventory.handler.ts
The only file that touches InventoryInternalService. If Inventory changes its internals, only this handler adapts. OrderModule is fully insulated — it doesn't even know this file exists.
export class ReserveInventoryHandler
  implements ICommandHandler<void, ReserveInventoryCommand> {

  constructor(private readonly inventorySvc: InventoryInternalService) {}

  async handle(cmd: ReserveInventoryCommand): Promise<void> {
    // Loads the aggregate, checks stock, marks items reserved, saves
    await this.inventorySvc.reserve(cmd.items, cmd.actorId);
    // ↑ Throws a DomainError if stock < requested qty
    // ↑ That error propagates to OrderAppService → order is NOT saved ✅
  }
}
// Lives INSIDE Inventory module. Private. Never exported. OrderModule never sees this.

// order/application/order.app.service.ts
import { ReserveInventoryCommand } from '@inventory/commands/reserve-inventory.command';
// ↑ The ONLY import from Inventory module. Everything else stays hidden. ✅

export class OrderAppService {
  async createOrder(dto: CreateOrderDto): Promise<void> {

    // ① Reserve inventory FIRST — synchronous, must succeed before we proceed
    await this.commandBus.execute(
      new ReserveInventoryCommand(dto.items, dto.actorId),
    );
    // ↑ If stock is insufficient → throws DomainError → order is NEVER saved ✅

    // ② Only if reservation confirmed — build and persist the order aggregate
    const order = Order.create(dto.items, dto.buyerId);
    await this.orderRepo.save(order);

    // ③ Publish domain events for async side-effects (notifications, analytics…)
    await this.eventBus.publish(order.pullDomainEvents());
  }
}
// OrderModule knows: ICommandBus, ReserveInventoryCommand — nothing else from Inventory ✅
🚦 CommandBus Flow — Order sends command without importing Inventory internals
🚨
The CommandBus Rule — Never Fire-and-Forget a Critical Write
🚨 Rule: Inventory reservation must be synchronous — never fire-and-forget it! If you use Domain Events for reservation, you commit the order to the DB first, then attempt to reserve later — creating a window where two concurrent orders can both succeed against the last unit of stock. The CommandBus keeps the sequence strict: reserve → confirm → then save the order. In that order. Always.
🎯 Real-World Scenario — Two Customers, One Pair of Shoes

Two customers click "Buy" simultaneously. Only 1 unit left in stock. Here is what happens with each approach:

Without CommandBus (using Events) With CommandBus ✅
Both orders save to DB concurrently ❌ First reservation wins. Second gets DomainError thrown immediately.
Event handler tries to reserve for Order 2 — stock is zero, fails — but order already exists ❌ Second order's reservation fails → order is never saved. DB stays consistent. ✅
Manual compensation saga required (cancel, refund, email apology…) 💀 No compensation. No saga. The write was atomic. Customer sees an immediate error. Clean.

The CommandBus also keeps team boundaries clean: the Orders team never needs to open Inventory's codebase. They send a typed command — same as calling an API, but in-process and with full TypeScript type-safety.

Synchronous read. Caller only imports a tiny query class. Handler inside User module adapts if anything changes.
// VendorService (caller)
const user = await queryBus.execute(new GetUserByIdQuery(id));
🛡
Use ACL (Anti-Corruption Layer)
Create a thin wrapper in the consumer module. Stable, same-team dep where you just want type isolation without full QueryBus setup.
// In Vendor module's infrastructure/
class UserACL {
  getOwnerView(id): VendorUserView { ... }
}

Quick Reference — 3 Patterns at a Glance

Module A needs something from Module B → pick ONE →
🛡 ACL
  • Same team owns both
  • Dependency is stable
  • Just want type isolation
  • Quick win needed
→ Create user-acl.ts in consumer's infrastructure/
🚌 QueryBus
  • Need sync answer NOW
  • Different teams possible
  • Service might change often
  • Maximum flexibility needed
→ Query class + handler, register on bus
⚡ Domain Events
  • It's a reaction, not a request
  • Eventual consistency is OK
  • Planning microservices
  • Zero coupling needed
→ Subscribe to events in other module

🧠 Memorize This — The 3-Pattern Rule of Thumb

🛡
ACL
Same team, stable API, just stop type leakage
🚌
QueryBus
Clean sync read that might change — default choice
⚡
Domain Events
Reactions & side-effects where eventual is fine

In most apps you use all three together: QueryBus for live data lookups, ACL for stable cross-context guards wrapped locally, and Domain Events for side-effects like "when a user is deleted, clean up their stuff."
